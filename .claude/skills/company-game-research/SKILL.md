# 缩写识别 + 主题研究 Skill

本 skill 解决一类典型问题：**用户提到的某个名字（缩写/代号/非完整名称）你不认识，但用户期望你研究它的某个主题**。

例如："研究 EVD 和 KBN 的运营策略"——EVD 和 KBN 是什么没说，但你必须先搞清楚才能研究。

## 触发场景示例

- "研究 Deca 的 EVD、KBN 两款游戏的运营策略"
- "调研 ABC 公司旗下 X 产品的版本演变"
- "未知缩写 XYZ 对应什么？请详细分析"
- "做一份 N 公司主题研究，要可信度分级"

## 核心原则（不可违反）

### 原则 1：分步骤执行 + 显式汇报
任务拆为 4 个原子步骤。每完成一步停下来汇报，等用户确认"继续"才进下一步。严禁连续执行多步而不汇报。

### 原则 2：禁止幻觉
搜索失败时直接报告"未找到"，禁止编造任何版本号、日期、功能名、数值。

### 原则 3：AI 摘要 ≠ 一手资源
WebSearch 返回的 AI 摘要不算来源。所有具体声明必须附带可点击访问的原始页面 URL（官方公告、应用商店版本历史、官方支持文档等）。仅有 AI 摘要支持的声明，标注为 UNVERIFIED。

### 原则 4：声明强制分级
报告中每条具体声明必须附带置信度标签：
- **HIGH**：≥2 个独立一手来源一致
- **MEDIUM**：单一权威一手来源
- **LOW**：仅有玩家社区/论坛/玩家自制内容支持
- **UNVERIFIED**：无一手来源，必须删除或显式标注

格式：`声明内容 [HIGH] [来源](URL)`

## 工作流（4 步原子任务）

### Step 1: 公司与目标识别

**目标**：搞清楚用户提到的公司是什么、旗下有哪些产品、缩写各自对应哪款产品。

**做法**：
1. 搜索公司全称、母公司、业务定位
2. 搜索该公司的游戏组合（acquisitions / portfolio / games list）
3. 如果用户指令中有未知缩写，用所有合理规则反向匹配（首字母、跳过连接词、拼音、副标题、内部代号等），直到锁定高置信度候选
4. 锁定候选后，用至少 2 个独立来源验证确实是该公司旗下游戏

**缩写匹配多策略**：
1. **首字母规则**：每个英文单词的首字母
   - 示例：缩写 RPS → Random Power Source（随机电源）
   - 适用：标准短语缩写，最常见

2. **跳过连接词规则**：跳过 of / for / the / and / : 等连接词后取首字母
   - 示例：缩写 IFS → **I**nstitute [for] **S**tudies（研究所），跳过中间的 for
   - 适用：包含介词或连接词的完整名称

3. **跳过中段规则**：保留首尾关键词，省略副标题主词
   - 示例：缩写 ABZ → **A**lpha[Beta]**Z**eta（跳过中间词 Beta）
   - 适用：副标题中段被压缩

4. **拼音规则**：中文名的拼音首字母
   - 示例：缩写 LDH → **L**i **D**a **H**ai（李大海）或拼音风格化简写
   - 适用：被命名物有中文名

5. **副标题规则**：仅取副标题的首字母
   - 示例：完整名"Project Phoenix: Battle Royale" → 缩写 BR（仅副标题）
   - 适用：主标题被忽略，仅记副标题缩写

6. **内部代号规则**：项目代号、开发代号、内部 ID
   - 示例：缩写"X-5"或"Project Atlas"这种代号风格
   - 适用：公司内部命名习惯泄漏到对外缩写

**汇报内容**：每个目标对象的全名、确认来源、置信度判断。

**汇报结束语**："Step 1 完成，识别结果如上，是否继续 Step 2？"

### Step 2: 主题信息搜集

**目标**：针对已确认的产品，按用户指定主题搜集具体信息。

**强制规则**：
1. 每条具体声明必须能定位到原始页面 URL（不是 AI 摘要的 URL）
2. 每条声明必须打置信度标签
3. 信息源优先级：官方公告 > 应用商店版本历史 > 官方支持文档 > 媒体报道 > 玩家社区
4. WebSearch 给出声明但无具体页面 URL → 二次搜索找原始页面 → 找不到则降级为 UNVERIFIED

**汇报内容**：HIGH/MEDIUM/LOW/UNVERIFIED 各多少条；最重要的 5 条声明示例。
**汇报结束语**："Step 2 完成，是否进入 Step 3 产出初稿？"

### Step 3: 初稿产出

**目标**：把 Step 2 的信息整理成结构化报告。

**保存路径**：`final_reports/{task}_draft.md`（task 由用户指定或从指令推断）

**强制要求**：
- 报告中**不包含任何 UNVERIFIED 声明**（删除或显式标注"待核实"）
- 所有具体声明保留置信度标签 + 原始 URL
- 报告末尾附置信度统计表

**汇报结束语**："Step 3 完成，初稿已保存，是否进入 Step 4 审查与修订？"

### Step 4: 红队审查 + 自动修订（闭环）

**目标**：发现错误 + 自动产出修订版报告。

**子步骤 4a：审查**
1. 抽取初稿中所有 HIGH/MEDIUM 置信度的具体声明
2. 对每条独立 fetch 原始页面验证一次
3. 找出与原报告不一致或可疑的声明
4. 输出审查报告 `final_reports/{task}_audit.md`，每条声明附"验证结果 / 来源 URL / 置信度判定"

**子步骤 4b：修订**
基于 audit 的发现：
1. 复制 draft 为 final 起点（draft 必须保留作证据，不可修改）
2. 对每条已确认错误的声明（❌ 标记），按 audit 提供的正确数据修正
3. 对每条降级声明（⚠️ HIGH→MEDIUM），修改置信度标签
4. 在 final.md **顶部**（标题之后、正文之前）添加修订日志：
  修订日志

  版本：{task}_final
  基于：{task}_draft.md
  审查：{task}_audit.md
  时间：YYYY-MM-DD

  修订 #N（对应 audit 编号 X）

  位置：[正文章节]
  修订前：[原文]
  修订后：[新内容]
  理由：[基于哪条 audit 发现]
  验证 URL：[原始来源]

  修订统计

  总声明数：N
  通过验证：X 条
  已修订错误：Y 条
  降级声明：Z 条

5. 保存为 `final_reports/{task}_final.md`

**强制要求**：
- 禁止直接修改 draft（它是审查证据）
- 修订必须基于 audit 的明确判定，禁止凭空修改
- 修订日志位置：**文件最顶部**——禁止以"附录"或"末尾说明"形式放在文件末尾
- 输出三件套：draft / audit / final

## 全局禁止事项

1. ❌ 跳步、连续执行多步
2. ❌ 编造任何具体内容
3. ❌ 引用 AI 摘要作为一手来源
4. ❌ 主动询问用户"XX 是什么"——必须自己研究
5. ❌ 修改 draft 文件
6. ❌ 把修订日志放在文件末尾

## 全局必做事项

1. ✅ 每步停下来汇报后等用户确认
2. ✅ 优先一手资源
3. ✅ 完成后做红队审查并自动修订
4. ✅ 输出三件套：draft / audit / final
5. ✅ 修订日志置顶

## 关于红队审查可信度的内部知识

红队审查（Step 4）通常比初始搜集（Step 2）准确，原因：
- 任务颗粒度小（单条声明 vs 整体研究）
- 目标具体（"声明 X 在原始页面吗"vs"搜集所有相关信息"）
- 工具更可靠（直接 fetch 原始 URL vs WebSearch 摘要）

但红队审查也有失效场景：
- URL 腐烂：原始 URL 内容已变化
- 页面截断：WebFetch 返回内容不完整
- 同工具同偏差：审查和初稿用同一工具，系统性错误无法发现
- 同域不同页：URL 正确但目标文本在同站点的不同页面

因此：审查发现的"通过"不等于 100% 正确，仍有 1-3 条潜在误差。报告应诚实标注"已知局限"。
